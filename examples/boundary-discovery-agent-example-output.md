# Example: boundary-discovery-agent output

This is a worked example of what `boundary-discovery-agent` produces, against a
fictional `settlement-instructions` service. It's here as a reference for what
"good" output looks like — not something to copy literally.

## Participants

| Surface | Participant | Connects to | Notes |
|---|---|---|---|
| Inbound API | `SettlementInstructionController` | SettlementService | POST /settlements — creates a settlement instruction |
| Inbound API | `SettlementQueryController` | SettlementInstructionRepository (direct read) | GET /settlements/{id} — bypasses service layer, reads repo directly |
| Jobs | `SettlementReconciliationJob` | SettlementService, ReconciliationLogRepository | Scheduled daily at 02:00, cron-configured |
| Jobs | `TradeEventConsumer` | SettlementService | Kafka listener, topic `trade.executed.v1` |
| Middleware | `ApiKeyAuthFilter` | SettlementInstructionController | Registered ahead of both controllers |
| Middleware | `AuditLoggingInterceptor` | SettlementInstructionController | Logs request/response; runs regardless of downstream outcome |
| Service/Algorithm | `SettlementService` | (orchestrates below) | No I/O of its own — delegates entirely |
| Algorithm/Rules | `SettlementAmountCalculator` | none (pure) | Rounding + fee calculation, no I/O |
| Algorithm/Rules | `CurrencyRoundingRule` | none (pure) | Currency-specific decimal precision rules |
| Database | `SettlementInstructionRepository` | Postgres | JPA repository |
| Database | `ReconciliationLogRepository` | Postgres | JPA repository, written only by the reconciliation job |
| External API | `FxRateClient` | vendor FX rate API | No OpenAPI spec found in repo — flagged below |
| External API | `CounterpartyNotificationClient` | vendor webhook | Pact contract found at `pacts/settlement-notifications.json` |
| Config | `SettlementProperties` | SettlementService, FxRateClient | Binds `settlement.*` properties; includes a feature flag `settlement.dry-run-mode` |

## Flagged for engineer attention

- `SettlementQueryController` reads the repository directly, bypassing `SettlementService` — worth confirming whether this is intentional (a legitimate read-only shortcut) or an inconsistency `api-inbound-test-agent` and `database-test-agent` need to coordinate on, since it's a different program-flow path than every other entry point in this module.
- `FxRateClient` has no OpenAPI/Avro/Pact contract found in the repo — `external-api-test-agent` will need to fall back to asking you directly for the vendor's response shape, or you can point it at a captured sample if one exists elsewhere.
- `settlement.dry-run-mode` in config changes behavior in both `SettlementService` and indirectly gates whether `FxRateClient` is called at all — flagged as a case where `config-test-agent` and `external-api-test-agent` will need to coordinate rather than test in isolation.
```

## 3. A genuinely ambiguous case (why "flag, don't guess" matters)

If the scan had also found a `NotificationDispatcher` class that both formats a message
*and* makes an outbound HTTP call, the agent should not silently file it under either
Jobs or External API — it should surface the ambiguity explicitly:

> `NotificationDispatcher` doesn't cleanly fit one surface — it's triggered by an internal
> event (job-like) but its only real behavior is an outbound HTTP call (external-API-like).
> I've listed it under External API for now since that's where the actual I/O risk sits,
> but flagging it so you can confirm or redirect it before specialists are assigned.
